## 1. 리니어 플로우 (요청분 — 짧게)

### ⚠️ 먼저 — 실사용 이력을 확인했다

`telepathy-v2/.claude/plans/progress.md`에 실제 연동 기록이 있다. 다만 **범위가 좁다.**

| 항목 | 실제 상태 |
|---|---|
| 부트스트랩 | 실행됨 — 팀 `HM`, 프로젝트 텔레파시, state·label 맵 6+10종 생성 |
| Phase 경계 자동 상태 전환 | 실행됨 — `last_action: update_phase:ideate→implement` |
| 마지막 동기화 | 2026-05-16 |
| 추적된 이슈 | **HM-41 1건** |
| **4버킷 drift 처리** | **`last_pull_hash: null` — 한 번도 실행된 적 없음** |

즉 아래 §해결의 4버킷 분류는 **설계만 있고 실행 이력이 없다.** 1인 개발이라 "팀원이 Linear에서 직접 바꾸는" 상황 자체가 발생하지 않았다.

**따라서 04는 두 갈래 중 하나로만 쓴다.**

- **(A) 실행된 것만 쓴다** — 부트스트랩 + Phase 경계 자동 전환 + 멱등성 + graceful degradation. 작지만 전부 사실이다.
- **(B) 설계임을 명시하고 쓴다** — "1인 개발이라 아직 실행되지 않은 설계"라고 밝히고 분류 원칙을 설명한다. 03의 한계 서술과 톤이 맞고, 오히려 정직해 보인다.

**(B) 권장.** 이 포트폴리오의 강점이 "한계를 아는 것"이라 (B)가 결이 맞는다. 단 **"운영했다"로 쓰면 안 된다** — 01~03의 신뢰까지 깎인다.

### 왜 이게 이야기가 되는가

"Linear를 연동했다"는 소재가 아니다. 팔 지점은 하나다.

> **자동 반영해도 되는 변경과, 사람이 봐야 하는 변경을 분류했다.**

이미 발행한 03의 "생략해도 되는 게이트와 안 되는 게이트가 다르다"와 **같은 판단의 반복**이다. 대상만 코드에서 협업 상태로 바뀐 것이라, 별도 주제가 아니라 같은 원칙의 두 번째 사례로 붙이면 글이 두꺼워지지 않는다.

### 문제

- 팀원이 Linear에서 직접 상태를 바꾸면 로컬 `progress.md`와 어긋난다.
- 매번 물으면 승인 피로가 쌓이고, 전부 자동 반영하면 사람 판단이 필요한 변경까지 덮어쓴다.

### 해결 — drift를 4버킷으로 분류

| 버킷 | 예시 | 처리 | 파일 수정 |
|---|---|---|---|
| **mechanical** | state, label, priority, assignee | 일괄 승인 1회 → 반영 | O |
| **textual** | 본문 편집, 새 코멘트 | 알림만 | X |
| **structural** | 신규 이슈·서브이슈 | 알림만 | X |
| **blocking** | Blocked 상태 | Phase 즉시 정지 + 강제 질문 | X |

핵심 규칙 3가지:

1. **기계적 변경만 자동 반영.** 텍스트·구조 변경은 절대 자동 수정하지 않는다 — 사람 판단이 필요한 영역이다.
2. **일괄 승인.** mechanical이 몇 건이든 질문은 1회. 승인 피로가 쌓이면 사람이 내용을 안 보고 누른다.
3. **에이전트는 사용자와 직접 대화하지 않는다.** 충돌 시 오케스트레이터로 에스컬레이션 → 3지 선택(로컬/원격/건너뜀) → 결정을 파라미터에 담아 재호출.

### 비용 통제 (곁들이면 좋은 디테일)

- **fast-skip** — 원격 snapshot의 SHA256이 직전과 같으면 drift 계산 전에 종료. 안 바뀐 경우 비용 0.
- **MCP 격리** — 전담 에이전트가 MCP 호출과 결과 파싱을 흡수해 오케스트레이터 컨텍스트를 오염시키지 않는다. 기계적 작업이라 모델도 값싼 쪽(Haiku)을 붙였다.
- **9개 action 전부 멱등** — 해시로 중복 판정. 같은 훅이 두 번 돌아도 이슈가 두 개 생기지 않는다.
- **실패가 파이프라인을 막지 않는다** — 동기화 실패는 한 줄 경고만 남기고 개발은 계속. OAuth 만료 시 Linear 훅만 끄고 GitHub 훅은 살려둔다.

### 분량 가이드

**`<details>` 1개, 04번으로.** 새 섹션 만들지 말 것. 4버킷 표 + 원칙 3줄 + 비용 통제 2줄이면 충분하다.
`ab-actkey`(우측 빨간 배지)는 `4버킷 분류` 정도.

## 2. 스킬 (미발행 — 넣을지 판단 필요)

현재 포트폴리오에 스킬 얘기가 **전혀 없다.** 자체 제작은 3개다.

### 2-1. harness-diagnostics — 가장 강한 소재

에이전트 협업 환경의 성숙도를 12원칙 × 4차원으로 채점하고 L1~L5 등급을 매기는 진단 스킬. 체크리스트는 코드베이스 84항목, 스킬 51항목.

**여기서 진짜 팔 것은 채점표가 아니라 이것이다:**

`adversarial-verify.sh` — 각 항목을 "통과했는가"가 아니라 **"실패 증거가 있는가"**로 다시 검증한다. 그리고 두 결과의 차이를 지표로 만들었다.

> **Bias Delta = Score(통과 수) − Confidence(근거가 확실한 통과 수)**
> 5 이상이면 "통과했지만 근거가 약한" 항목이 많다는 뜻 → 자기 평가의 긍정 편향 의심

자기 자신도 같은 기준으로 진단한다(self-referential). 즉 **AI가 스스로 매긴 점수를 믿지 않는 장치를 점수 체계 안에 넣은 것**이다.

### ✅ 실사용 이력 확인됨 — 04와 달리 근거가 있다

`CHANGELOG.md`에 측정된 before/after가 남아 있다.

> `[2.1.0]` — **adversarial-verify Bias Delta: 1 → 0** (low-confidence 항목 해소)

같은 릴리스의 다른 항목도 전부 원칙 점수가 끌고 간 변경이다.

- SKILL.md 산문 12줄을 별도 참조 문서로 분리 → **P2(Map) 순도 향상**, 118줄 → 107줄
- `adversarial-verify.sh`에 "왜" 주석 6건 추가 → **P12(Self-Documentation) 향상**
- 가중치·체크리스트 항목 수 결정 근거를 ADR 2건으로 분리

**진단 도구가 자기 점수를 낮게 매긴 지점을 스스로 고쳐 버전을 올린 기록**이다. 04(설계만 있음)와 달리 이건 그대로 써도 된다.

이건 공고의 "한계를 설명할 수 있는 분"과 직결된다. 03의 한계 4가지가 *회고*라면, 이건 한계를 *상시 측정 장치*로 만들고 그 지표로 자기 자신을 고친 사례다. 한 단계 위다.

### 2-2. dev-interviewer / portfolio-interviewer

요구사항·경력을 단계형 분기 질문으로 끌어내는 스킬. 사용자가 스스로 표현하지 못한 제약·Anti-scope·기각한 선택지를 누적 30~50개 질문으로 뽑아낸다.

설계 의도가 한 줄로 정리된다 — **"AI가 복제하기 어려운 건 결과물이 아니라 판단의 해상도"**라서, 그 해상도를 질문으로 강제 추출한다.

다만 포트폴리오 소재로는 약하다. 검증된 산출 지표가 없고, 인터뷰 스킬이라는 게 심사자에게 곧바로 와닿지 않는다.

### 권장

**harness-diagnostics만 넣고 나머지 2개는 뺀다.** Bias Delta 하나로 승부가 나고, 인터뷰 스킬 2종은 같은 카드 안에서 인상을 흐린다.

분량은 `<details>` 1개(05번). `ab-actkey`는 `Bias Delta` 또는 `12원칙 · L1~L5`.

## 4. 최종 구성 제안

기존 카드에 `<details>` 2개만 추가한다. **새 섹션·새 CSS 불필요.**

```
AI 에이전트 개발 플로우  (발행 완료)
├─ [도표] 파이프라인
├─ 01 권한을 좁혀야 결과를 검수할 수 있다      ← 발행됨
├─ 02 AI 퀴즈 — 게이트를 끈 판단과 켠 판단      ← 발행됨
├─ 03 한계 — 도구가 빨라져서 새로 생긴 문제     ← 발행됨
├─ 04 협업 상태 동기화 — 4버킷 분류            ← 신규 (요청분)
└─ 05 하니스 자가 진단 — Bias Delta            ← 신규 (권장)
   [ab-aibox] 관통 원칙
```

`ab-aibox`(맨 아래 원칙 4줄)는 04·05를 추가해도 그대로 유효하다. 오히려 "경계 / 정지 / 보수성 / 누적" 중 **보수성**이 04·05로 뒷받침되면서 강해진다.

## 5. 검증 결과 요약

두 후보의 근거 강도를 실제로 대조했다. **결론이 갈린다.**

| | 04 리니어 | 05 하니스 진단 |
|---|---|---|
| 실행 흔적 | 텔레파시 1건 (HM-41) | CHANGELOG 버전 이력 |
| 핵심 소재 실행 여부 | ❌ 4버킷은 `last_pull_hash: null` | ✅ Bias Delta 1 → 0 측정됨 |
| 측정된 개선 | 없음 | 있음 (P2·P12 점수가 끌고 간 변경) |
| 쓸 수 있는 톤 | "설계했다" | "측정하고 고쳤다" |

**05가 04보다 근거가 강하다.** 요청하신 04를 넣되, 05를 같이 올리면 04의 약한 근거가 상쇄된다. 반대로 04만 추가하면 기존 01~03(전부 실행 근거 있음)보다 밀도가 떨어지는 항목이 하나 붙는 셈이다.

## 6. 남은 판단

- **04를 "Linear"로 명시할지, "이슈 트래커"로 일반화할지.** 하니스는 GitHub Projects·Linear 양쪽 + dual-sync를 지원한다. 이직 맥락에서는 "협업 상태 동기화"가 안전하다 — 지원 회사가 Jira를 쓸 수도 있다. 다만 실제 돌린 건 Linear뿐이므로, 일반화하면 서술이 더 추상적이 되어 근거가 더 옅어 보이는 역효과도 있다.
- **04를 아예 05로 합칠지.** 둘의 공통 원칙이 "자동 처리할 것과 사람이 볼 것을 분류한다"로 같다. 카드 하나에 두 사례로 묶으면 `<details>` 1개로 끝나고 04의 근거 약점도 덜 드러난다.
