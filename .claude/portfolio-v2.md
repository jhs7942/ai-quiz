# AI Quiz — 시험 범위 고정이라는 제약을 역이용한 교재 기반 학습 퀴즈 플랫폼

> 과락 누적 시 강제 퇴소인 싸피 AI 시험 앞에서, **4시간 MVP** 제약 안에 LLM 동적 생성 대신 **싸피 교재 기반 정적 JSON**을 택함 → 1 캠퍼스 기획이 전국 캠퍼스로 유기적 확산, **답변 73,848건 · 접속 21,428건** 도달. 코드 개발 1인 + 콘텐츠 팀 2명.

**기간** · MVP 4시간 + 1·2차 시험 대비 개선 (2주 간격)
**역할** · 코드 개발 1인 + 기술적 의사결정 단독 / 퀴즈 콘텐츠 팀 2명 분담
**스택** · React 19, Vite, TypeScript, Zustand, Supabase, Tailwind, Vercel

---

## Context

**소속·동기** — **SSAFY 마이스터고 트랙** 재학 중 AI 평가 시험 대비. 트랙 기준 **총 12회 시험 중 5회 과락 누적 시 강제 퇴소**. 본인은 6회차 시점 과락 0/5로 여유 있었으나, AI 이론의 커리어 가치를 높게 판단해 단순 통과가 아닌 **"제대로 학습할 도구"** 가 필요.

**시간 제약** — 시험까지 2일, MVP 데드라인 4시간.

**자원 제약** — 코드 개발 1인 + 퀴즈 콘텐츠 팀 2명 분담.

**도구·스킬 제약** — Claude Code Pro 토큰 한도. 개인 숙련도: **Vite·Supabase 첫 사용, Claude Code 1개월 누적**. 4시간 완성은 **"AI 도구가 숙련도 공백을 메울 수 있다"는 가설에 근거한 도박**.

**사용자 가설** — 재학생 약 **1,000명**이 각자 NotebookLM으로 퀴즈를 만들던 상황. "한 번 만들면 1,000명 전체가 쓸 수 있다"는 **집합재 가설**이 동기 — 본인용이 아닌 학과 공통 인프라로 설계.

**도메인 특성** — AI 과목은 개념 + 수식·코드 혼합형. 하나의 개념이 한글·영문으로 공존(과적합 / Overfitting) → 주관식 유연 채점의 필수 조건.

**데이터 성격** — 로그인 없음, PII 없음, 공개 학습 데이터만.

---

## Problem

**기존 경로의 구조적 한계** — 싸피 강사가 NotebookLM 기반 자체 퀴즈 제작을 권장해 반 친구들 대다수가 이를 따랐으나, 1 사이클(업로드→생성→풀이)에 **평균 10분** + **데스크탑 전용**이라 지하철·자투리 시간 활용 불가.

**집합재로서의 비효율** — 친구들은 만든 퀴즈를 **PDF로 단체방에 공유**했으나, 인터랙티브 풀이·채점 불가 + 각자 중복 제작으로 집합적 시간 낭비.

**비용의 비대칭성과 진짜 동기** — 본인은 과락 여유가 있었고 목표도 "과락(60점) 면하기"라는 낮은 기준이었으나, **과락 4개 이상 누적된 동료들**에게는 퀴즈 도구 품질이 곧 퇴소 리스크. 진짜 동기는 **"과락 위기 친구 돕기"** — 개인 효용이 아닌 커뮤니티 기여로 정의된 Problem.

## Analyze

| 선택지 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. LLM API 동적 생성 (Next.js API Routes) | 무한 콘텐츠 확장 | **시험 범위 적합도 보장 불가** (LLM은 싸피 교재 모름), API 구현 시간 소요 | **구상 단계 기각 — API 미구현** |
| B. 싸피 교재 기반 JSON 사전 제작 (생성형 AI 초안 + 인간 검수) | 시험 범위 완전 일치, 즉시 응답, 0원 | 재배포 시 콘텐츠 업데이트 | **채택** |
| C. 순수 수동 작성 | 최고 품질 | 하이브리드 대비 시간 효율 낮음 | 기각 |

**핵심 판단 기준** — "시험 범위가 싸피 내부 교재로 고정"이라는 제약이 결정적. LLM 동적 생성은 범위 적합도를 구조적으로 보장할 수 없음. **교재 기반 + 생성형 AI 초안 + 인간 검수** 하이브리드로 범위·정확도 모두 확보.

**실측 근거**
- v1 LLM 샘플 검수: **30개 중 1개 오류** (범위 밖 문제·중복 내용) — 품질 자체는 낮지 않았으나 **"범위 이탈" 타입**이라 교재 기반의 우위 확인.
- 하이브리드로 팀 2명이 **1차 시험용 930개(과목 420 + 모의 270 + 재시험 240) 생성·검수에 약 2시간**, 2차 시험용 180개 추가.

## Hypothesis

**4가지 사전 가설**

1. **속도** — 퀴즈 로드 < 1초
2. **비용** — 사용자별 추가 비용 0원
3. **가용성** — DB 장애 시에도 퀴즈 풀기 기능 유지
4. **시험 범위 적합도** — 교재 기반이므로 실제 출제 범위와 높은 겹침률

**검증 방법 — 사후 관찰만 (사전 측정 프로토콜 부재)** — 4시간 데드라인에서 측정 인프라 구축은 오버헤드라 판단. 대신 **롤백 비용이 낮은 구조**(정적 JSON + Vercel 재배포)로 "가설 실패 → 빠른 교정"을 설계적으로 확보.

**의도적으로 세우지 않은 가설 — 주관식 채점 정답률** — 객관식 우선 설계의 스코프 분리 판단. 이게 Result에서 **숨겨진 반증**의 진원지가 됨 → Learnings의 핵심 소재.

## Action

**실행 요약**
v1(Next.js + LLM API) 구상 단계 기각 → v2(Vite + 정적 JSON) 구축. Supabase는 분석·로깅 전용으로 축소, 모든 DB 호출 silent fail. NotebookLM 기반 강의→퀴즈 파이프라인으로 팀 2명이 1,110문제 생성·검수.

**트레이드오프**
- 포기: 실시간 콘텐츠 업데이트, 관리자 대시보드, **문제당 정답률 표시** (본인이 UX 오버헤드로 반대 주도)
- 기술 부채: 주관식 "괄호 패턴 확장" 수준 규칙 (정답률 40.7%)
- 보안 타협: RLS 전면 비활성화

**설계 성격 — 사전 설계형 + 학습형 혼합**
- **사전 설계형** — silent fail 원칙("DB 죽어도 퀴즈는 돈다")은 초기 설계부터 명시. 모든 Supabase 호출이 이 원칙을 따름.
- **학습형** — RLS 전면 비활성화는 **401 에러 후의 대응**. 4개 대안(SELECT 정책 / `return=minimal` / 클라이언트 UUID / 전면 비활성화)을 검토, "anon key + PII 없음 + 공개 데이터" Context에서 **RLS 본래 목적 부적용**이 근거.

**배치 저장 롤백의 정량 근거 (교차 검증)**
- 상한: 2일 × 1,000명 이하 × 500MB 무료 한도 → 여유 충분
- 실측: 사용자 1명당 **초당 1회 미만** 호출 (Supabase 대시보드)
- 두 근거 모두 **한도의 10% 미만** → 최적화 도입 기준(30%)에 한참 못 미침 → 롤백

**시간 배분 — 가장 오래 걸린 건 "요구사항 협의"**
4시간 중 팀원과의 요구사항 협의가 병목. 구현이 아니라 **"무엇을 안 할지 정하는 과정"** 이 핵심 시간 자원.

**의도적 비범위 (Anti-scope) — 즉시 확정**
- UI 프로토타입·디자인 평가 에이전트 미사용 (기능 완성 > 디자인, 토큰 한도)
- 기기 간 진도 동기화 미구현 (로그인 복잡도)
- **PWA 미도입 확정** (Vite 8 peer dep 실패 후 반응형 웹으로 대체)
- 문제당 정답률 표시 삭제 (UX 오버헤드)

**실사용 니즈로 포기한 Anti-scope**
- 단순 적재 전략 (결과 확인 시에만 DB 적재) → 중도 이탈 데이터 손실 때문에 포기, 문제마다 + 완료 시 이중 적재로 확장

**자기 회고 — 스코프 판단의 오류 인정**

| 항목 | 원래 판단 | 실제 | 반성 |
|---|---|---|---|
| **오답노트 기능** | "로그인 없이 불가" → 미구현 | **로컬스토리지로 구현 가능**했음 | 스코프를 너무 빠르게 좁힘 |
| **협업 툴(Linear) 미도입** | "4시간 MVP엔 오버헤드" | 업무 분배 불균형 → **팀원 소외감** | 협업 인프라를 속도의 반대로 오해. **후속 `how_many`에서 Linear 도입의 직접 계기** |

**팀 구조 & 협업**
- 본인: 코드 + 기술적 의사결정 단독. 팀원 2명: 콘텐츠 제작·검수
- 기술 결정은 본인 단독 (팀원 반대 없음). 요구사항은 팀 합의 ("정답률 표시 삭제"는 본인 주도 반대)

**사용자 확보와 피드백 수집**
- 확산: **싸피 15기 메타모스트 단체방 공지 1회** → 1,000명 대상 유기적 확산
- 수집: 앱 내 신고 버튼 **134건, 반영률 ~90%** (주관식 개선, 오답노트, 다크 모드 등)
- 결정적 피드백 2건:
  - **사용자 제안** "로그인 없이도 로컬스토리지 활용 가능" → 오답노트 Anti-scope 회고의 근거
  - **싸피 강사** "단순 기능 구현은 포트폴리오에 쓸 수 없다" → **프로젝트 방향을 "무엇을 만들었는가"에서 "어떤 판단을 내렸는가"로 전환**한 외부 신호

**가장 뼈아픈 스토리 — 팀원 소외감의 반복**
콘텐츠 팀원 2명이 업무 분배 불균형으로 소외감 → **진로 고민**까지 갔으나 즉시 대응 실패, **프로젝트 종료 후 회고로 깨달음**. 후속 `how_many`에서 **같은 패턴 반복** — 신규 팀원 2명이 테스크 분배 부재로 **이탈**. 이탈한 팀원이 다른 프로젝트에서 활약하는 모습을 보며 *"내가 사람을 잃게 만들었다"* 는 미안함 체감 → **Linear 도입**의 감정적·구조적 계기.

## Learnings

**회고 1 — 학습 목표의 이중성**
Context의 두 동기 중 **62점은 과락 면하기만 달성**. 그러나 싸피 교재 직독과 1,160 퀴즈 검수로 **간접 학습이 대량 발생** — 시험 점수로는 미달이나 **학습의 질로는 초과**. "무엇을 학습으로 정의하는가"에 대한 기준 전환.

**회고 2 — 지금 다시 시작한다면**
- **Linear 기반 테스크 분배를 첫 30분에 세팅** (팀원 소외감의 구조적 뿌리가 업무 분배 비가시성이었음, 후속 프로젝트에서 팀원 이탈의 대가를 치른 후 체득)
- 최적화는 실측 지표가 한도의 30%를 넘기 전까지 도입 보류
- 기능 단위 분리 커밋 강제 (PWA·배치·RLS 일괄 배포 → 4커밋 롤백 경험)
- 주관식 채점에도 사전 가설·측정 지표 정의

**남은 한계**
- 주관식 정답률 40.7% → 파인튜닝 로드맵
- 난이도 필드와 실측 정답률 불일치 → 재보정 미완
- PWA는 Anti-scope 확정 (반응형 웹 대체)

**다른 상황에 이식 중인 3가지 원리**

1. **제약이 기술 선택을 강제한다** — 4시간·토큰 한도가 Vite·JSON을 고르게 했다. *제약이 많을수록 "덜 하는 것"이 승리 전략*. 이후 모든 프로젝트에서 "이 제약이 내 선택을 어떻게 좁혀주는가"를 먼저 확인.

2. **아키텍처가 가용성을 결정한다** — 재시도·미들웨어가 아니라 *"JSON=필수, DB=선택"* 이라는 **구조 자체**가 silent fail을 가능케 함. 설계 초기에 "무엇이 죽어도 무엇이 살아야 하는가"를 먼저 그리는 습관.

3. **협업 인프라 부재 = 사람을 잃는 비용** — 두 번의 팀원 이탈 경험으로 *"협업 도구는 속도의 반대가 아니라 속도의 전제"* 라는 인식 전환. `how_many` 이후 **Linear 도입**. 프로젝트 첫 30분을 팀 구조 설정에 투자하는 것이 기본값.

**메타 회고 — 이 포트폴리오 자체의 재작성**
싸피 강사의 *"단순 기능 구현은 포트폴리오에 쓸 수 없다"* 피드백이 이 문서 재작성의 동기. 기능 목록이 아니라 **(1) 제약 하의 기술 선택, (2) 측정 없는 최적화의 실패, (3) 협업 인프라 부재의 대가** 세 축으로 읽혀야 이 프로젝트의 진짜 가치가 드러남.
