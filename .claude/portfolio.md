## 1. 아키텍처 전환: "왜 LLM API를 버리고 JSON으로 갔는가"

### 고민

v1은 NotebookLM에서 영감을 받아 "사용자가 LLM API 키를 입력하면 실시간으로 퀴즈를 생성"하는 구조였다. Next.js API Routes로 Gemini/GPT/Claude를 호출하고, 결과를 파싱해 퀴즈로 보여주는 방식.

문제는 세 가지였다.

| 문제 | 구체적 상황 |
|------|-----------|
| 비용 전가 | 사용자가 본인 API 키를 입력해야 하는 UX — 일반 사용자에게 API 키 발급은 높은 진입 장벽 |
| 품질 불안정 | LLM이 생성하는 퀴즈의 정답이 틀리거나, 보기가 중복되는 등 품질 편차가 컸음 |
| 속도 | 10문제 생성에 10~30초 — 시험 직전 급하게 공부하는 상황에서 대기 시간이 학습 흐름을 끊음 |

### 결정 과정

"퀴즈 데이터가 동적이어야 하는가?"라는 질문으로 돌아갔다. 내가 만든 강의 자료 기반 퀴즈는 범위가 고정되어 있고, 한 학기 동안 바뀌지 않는다. 동적 생성의 이점이 없었다.

### 대안 비교

| 항목 | v1: LLM API 동적 생성 | v2: JSON 사전 제작 |
|------|---------------------|-------------------|
| 프레임워크 | Next.js (API Routes 필요) | Vite (서버 불필요) |
| 퀴즈 품질 | LLM 출력 의존, 불안정 | 사전 검수 가능, 피드백으로 개선 |
| 비용 | 사용자 API 키 필요 | 0원 |
| 속도 | 생성 10~30초 | 즉시 (JSON fetch) |
| 오프라인 | 불가 | 가능 (정적 파일) |
| 확장성 | 무한 (프롬프트 변경) | JSON 파일 추가 필요 |

**결론**: 확장성을 포기하는 대신, 비용·품질·속도를 모두 확보했다. "시험 2일 전"이라는 제약이 이 결정을 더 쉽게 만들었다 — 정교한 시스템보다 지금 쓸 수 있는 도구가 필요했다.

## 2. 프레임워크: "왜 Next.js가 아니라 Vite인가"

### 고민

v1에서 Next.js를 쓴 이유는 API Routes 때문이었다. LLM API 키를 서버 사이드에서 안전하게 처리해야 했으므로 서버가 필요했다.

v2에서 API를 제거하자 서버 존재 이유가 사라졌다. JSON 파일을 브라우저에서 fetch하는 것이 전부다.

### 결정 근거

| 기준 | Next.js | Vite |
|------|---------|------|
| 서버 필요성 | 불필요해짐 (API 제거) | 불필요 (SPA) |
| 빌드 속도 | 상대적으로 느림 | 빠름 |
| 배포 복잡도 | 서버리스 함수 설정 | 정적 파일만 |
| 토큰 소모 | 설정 파일·구조가 복잡해 Claude Code 토큰 소모 높음 | 단순 구조로 토큰 절약 |

**Claude Code Pro 요금제의 토큰 한도**가 숨은 제약이었다. Next.js의 복잡한 설정(App Router, 서버 컴포넌트 구분, 미들웨어 등)은 Claude Code가 코드를 생성할 때 더 많은 토큰을 소모한다. Vite + React SPA는 구조가 단순해 같은 토큰으로 더 많은 기능을 구현할 수 있었다.

## 3. 퀴즈 데이터 생성 파이프라인: "강의를 퀴즈로 바꾸는 워크플로우"

### 고민

1,160문제를 수작업으로 만드는 것은 불가능했다. 강의 내용을 자동으로 퀴즈로 변환하는 파이프라인이 필요했다.

### 파이프라인 진화

**초기 방식 (Whisper 기반)**

```
강의 다운로드 → 쉬는시간 기준 분할 → Whisper로 전사 → NotebookLM에서 퀴즈 생성
```

수동 작업이 많았다. 다운로드, 분할, Whisper 설치·실행까지 사전 준비에 시간이 걸렸다.

**현재 방식 (Alt 기반)**

```
유튜브 강의 재생 + Alt 앱 실행 → 텍스트 내보내기 → NotebookLM에서 퀴즈 생성
```

실시간 전사로 사전 준비 단계를 제거했다. 강의를 듣는 동시에 텍스트가 생성된다.

### 대안 검토

| 방식 | 장점 | 단점 | 채택 |
|------|------|------|------|
| 수동 작성 | 품질 최고 | 1,160문제 비현실적 | X |
| LLM API 직접 호출 | 유연함 | 프롬프트 튜닝 필요, 품질 편차 | X |
| Whisper + NotebookLM | 자동화 | 사전 준비 번거로움 | 초기 |
| Alt + NotebookLM | 실시간, 간편 | Alt 앱 의존 | 현재 |

**핵심 판단**: 퀴즈 "생성" 자체는 NotebookLM이 가장 잘 했다. 병목은 STT(음성→텍스트) 단계였고, 이를 실시간 전사로 해결했다.

## 4. 상태 관리: "Zustand + sessionStorage로 충분한가"

### 고민

퀴즈 풀이 중 새로고침하면 진행 상황이 사라지는 문제. 학생들이 시험 직전에 쓰는 도구이므로 "풀다가 날아감"은 치명적이다.

### 결정 과정

| 선택지 | 장점 | 단점 |
|--------|------|------|
| Redux + localStorage | 업계 표준 | 보일러플레이트 과다, 4시간 안에 비효율적 |
| Zustand + sessionStorage | 설정 최소, persist 미들웨어 한 줄 | 탭 간 공유 불가 (문제 없음) |
| 서버 사이드 상태 | 기기 간 동기화 | 로그인 필요, 복잡도 급증 |

Zustand의 `persist` 미들웨어로 sessionStorage 연동이 한 줄이었다. 새로고침해도 현재 문제, 선택한 답변, 채점 결과가 유지된다. 탭을 닫으면 초기화되지만, 퀴즈 앱에서 탭 간 상태 공유는 필요 없었다.

## 5. DB 아키텍처: "Supabase를 분석 전용으로 제한한 결정"

### 고민

퀴즈 데이터를 DB에 넣을지, 정적 JSON으로 서빙할지. DB에 넣으면 관리 대시보드, 실시간 업데이트가 편하지만, 정적 파일이면 서버 의존성이 사라진다.

### 결정: "퀴즈는 JSON, 분석만 DB"

```
퀴즈 데이터:  public/quizzes/*.json  →  브라우저 fetch
분석/로깅:   Supabase (users, access_logs, quiz_sessions, quiz_answers, feedbacks)
```

**핵심 원칙 — "DB가 죽어도 퀴즈는 돈다"**

모든 Supabase 호출을 silent fail로 처리했다. DB 장애, 네트워크 오류, Supabase 무료 플랜 한도 초과 — 어떤 경우에도 퀴즈 풀기 기능은 영향받지 않는다. 시험 직전이라는 사용 맥락에서, 통계 데이터 누락보다 퀴즈가 안 돌아가는 것이 더 큰 문제다.

### 이 결정이 만든 트레이드오프

| 얻은 것 | 포기한 것 |
|---------|----------|
| 완전한 오프라인 퀴즈 | 실시간 문제 업데이트 (재배포 필요) |
| 서버 장애 내성 | 관리자 대시보드 (DB 쿼리 직접 실행) |
| 배포 단순화 (정적 파일) | 사용자별 진도 추적 (기기 간 불가) |

## 6. RLS 정책의 함정: "INSERT가 되는데 데이터가 없다"

### 고민

`users`, `access_logs`는 정상 저장되는데 `quiz_sessions`만 401 에러가 발생했다. INSERT 정책은 설정되어 있었다.

### 분석 과정

Supabase JS SDK의 `.insert().select('id').single()` 체인이 내부적으로 어떻게 동작하는지 추적했다.

```
클라이언트: .insert(row).select('id')
→ PostgREST: INSERT + Prefer: return=representation
→ INSERT 성공 (INSERT 정책 통과)
→ 반환용 SELECT 실행 (SELECT 정책 부재 → 401)
→ 트랜잭션 롤백 → 행 자체가 생성되지 않음
```

**핵심 발견**: INSERT 정책만으로는 `.select()` 체이닝과 호환되지 않는다. PostgREST의 `return=representation` 동작이 암묵적으로 SELECT 권한을 요구한다.

### 대안 비교

| 방법 | 설명 | 채택 |
|------|------|------|
| SELECT 정책 추가 | INSERT + SELECT 둘 다 허용 | X — anon이 전체 테이블 읽기 가능해짐 |
| `.select()` 제거 + 클라이언트 UUID | ID를 클라이언트에서 생성, 반환값 불필요 | X — 기존 코드 변경 범위 넓음 |
| `return=minimal` 명시 | 반환 없이 INSERT만 | X — 일부 로직에서 반환값 사용 중 |
| **RLS 전면 비활성화** | anon key 구조에서 RLS가 불필요 | O |

### 결정 근거

이 프로젝트는 로그인이 없고, 모든 데이터가 익명 기여분이며, PII(개인식별정보)를 포함하지 않는다. RLS의 "행 단위 접근 제어"라는 본래 목적이 적용되지 않는 구조다. 유지하면 복잡도만 증가하고 이번처럼 예상치 못한 에러의 원인이 된다.

단, RLS 해제는 **읽기 노출**도 함께 발생시킨다. `.select('*')` 한 번으로 테이블 전체 dump가 가능하다. 공개 학습앱이고 민감 데이터가 없어 허용했지만, 이 점은 의식적으로 수용한 것이다.

## 7. 배치 저장 → 즉시 저장 회귀: "추측 기반 최적화의 교훈"

### 고민

두 가지 문제가 동시에 있었다.

1. 퀴즈 중도 이탈 시 답안 데이터 100% 유실
2. Supabase 무료 플랜 트래픽 한도에 대한 우려

"5문제 단위 배치 저장"으로 두 문제를 동시에 해결하려 했다.

### 첫 번째 시도: 배치 저장 (커밋 494ea8e)

```
문제 1~5 채점 → 5문제 모아서 한 번에 INSERT → 유실 최대 4문제
```

도입 후 리뷰에서 HIGH 이슈가 발견됐다.

| 이슈 | 설명 |
|------|------|
| clearAnswer 후 중복 INSERT | 답변 삭제 → 재채점 시 동일 답안이 두 번 저장될 수 있음 |
| fire-and-forget 카운트 갱신 | 저장 실패해도 카운트가 증가해 해당 배치 영구 유실 |
| flush 타이밍 복잡도 | 퀴즈 종료, 페이지 이탈, 배치 경계 등 다중 트리거 관리 필요 |

### 회귀 결정 (커밋 900d8c0)

| 항목 | 배치 저장 | 즉시 저장 |
|------|----------|----------|
| Supabase 요청 수 | 1/5 | 문제 수만큼 |
| 중도 이탈 유실 | 최대 4문제 | 0문제 |
| 구현 복잡도 | 높음 (Set 추적 + flush + 재시도) | 낮음 |
| 중복 삽입 리스크 | 존재 (리뷰 HIGH) | 없음 (UPSERT) |

**핵심 판단**: Supabase 요청량을 실측한 결과, 사용자 1명당 초당 1회도 안 되는 호출량이었다. 무료 플랜 한도와 거리가 멀었다. 존재하지 않는 문제를 해결하려다 실재하는 버그를 만든 셈이다.

### 얻은 교훈

**YAGNI(You Aren't Gonna Need It)의 실전 사례**. 지표를 측정하지 않은 상태에서 추측으로 최적화를 도입하면, 이점은 없으면서 복잡도와 버그 위험만 추가된다.

최적화 도입 전 체크리스트:
1. 현재 지표를 먼저 측정했는가?
2. 한도의 30% 이내라면 보류해도 되는가?
3. 되돌리기 쉬운 변경인가?
4. 유실 허용 범위(SLO)를 정의했는가?

## 8. SPA에서 AdSense 승인 받기: "CSR의 구조적 한계와 하이브리드 전략"

### 고민

AdSense 신청이 반려됐다. 사유: "게시자 콘텐츠가 없는 화면에 Google 게재 광고".

SPA(CSR)는 Google 크롤러가 방문하면 빈 `<div id="root"></div>`만 본다. JavaScript를 실행해야 콘텐츠가 렌더링되는데, 크롤러가 JS를 실행하지 않으면 빈 페이지로 판단한다.

### 대안 비교

| 방법 | 설명 | 채택 |
|------|------|------|
| Next.js로 전환 (SSR) | 서버에서 HTML 생성 | X — 아키텍처 전면 교체, 비용 대비 효과 낮음 |
| 전체 페이지 Prerender | 빌드 시 모든 페이지 HTML 생성 | X — /quiz, /result는 상태 의존이라 prerender 불가 |
| **하이브리드 Prerender** | 정적 페이지만 prerender, 동적 페이지는 CSR 유지 | O |

### 하이브리드 전략

```
정적 페이지 (/, /about, /contact, /privacy, /report)
  → 빌드 시 HTML 미리 생성 → 크롤러가 콘텐츠 확인 → AdSense 광고 삽입

동적 페이지 (/quiz, /result)
  → React CSR 유지 → 상태 의존 페이지이므로 prerender 불가 → 광고 제외
```

추가로 Footer에 About/Contact/Privacy 링크를 추가하고, Report 페이지에 서비스 성과 데이터를 노출해 "콘텐츠가 있는 사이트"임을 증명했다.

## 9. 트래픽 대응: "정적 SPA의 장점을 극대화"

### 고민

시험 기간에 동시 접속자가 몰릴 수 있다. 서버가 죽으면 시험 직전 학생들이 학습 도구를 잃는다.

### 결정: 정적 SPA 구조 자체가 최선의 방어

서버리스 아키텍처를 의도적으로 선택한 것이 트래픽 대응의 핵심이었다. JSON 데이터를 fetch하는 것이 전부이므로 서버 과부하 위험이 구조적으로 낮다.

추가 대응으로 검토한 5가지 방안:

| 방법 | 효과 | 우선순위 |
|------|------|---------|
| CDN 배포 (Vercel) | 글로벌 캐시, 원본 서버 부담 제거 | 이미 적용 |
| 브라우저 캐싱 | 재방문 시 서버 요청 0건 | 자동 적용 (Vite 빌드 해시) |
| Service Worker (PWA) | 오프라인 지원, 재방문자 완전 캐시 | 도입 후 롤백 (아래 참조) |
| Supabase 요청 배치 | DB 요청 절감 | 보류 (한도 여유 충분) |
| JSON 번들링 | HTTP 요청 수 감소 | 보류 (현재 체감 불필요) |

### PWA 도입과 롤백

Service Worker를 통한 오프라인 지원을 시도했으나 `vite-plugin-pwa`와 Vite 8의 peer dependency 호환 문제로 Vercel 빌드가 실패했다. 로컬에서는 `--legacy-peer-deps`로 우회했지만 CI 환경에서는 재현되었다.

이 과정에서 **여러 기능을 동시에 배포하는 위험**을 체감했다. PWA + 배치 저장 + RLS 수정을 한꺼번에 배포한 결과, 어떤 변경이 빌드 실패의 원인인지 분리가 불가능했다. 결국 `git reset --hard`로 4개 커밋을 롤백하고 하나씩 재배포했다.

**교훈**: 기능별 분리 커밋 + 개별 배포. 한 번에 하나만 바꿔야 문제 원인을 특정할 수 있다.

## 10. 주관식 채점: "한글과 영문을 동시에 인정하는 유연 채점"

### 고민

AI 과목 특성상 하나의 개념에 한글명과 영문명이 공존한다. 정답이 `"과적합(Overfitting)"`일 때 `"과적합"`, `"Overfitting"`, `"overfitting"`, `"과 적 합"` 모두 정답으로 인정해야 한다.

### 대안 비교

| 방법 | 설명 | 한계 |
|------|------|------|
| 정확 일치 | `userAnswer === answer` | 대소문자·공백 차이로 오답 처리 |
| 정규화 + 정확 일치 | 공백 제거 + 소문자 변환 후 비교 | `"과적합"`과 `"Overfitting"` 불일치 |
| **정규화 + 괄호 확장** | `"한글(English)"` 패턴에서 각각 분리 | 의미적 유사어 불가 (현재 한계) |
| LLM 기반 의미 채점 | 동의어까지 판정 | API 비용, 지연 시간 |

### 채택한 방식: 괄호 패턴 확장

`"과적합(Overfitting)"` → `["과적합(overfitting)", "과적합", "overfitting"]` 세 변형을 모두 정답으로 인정한다. 공백 제거와 소문자 변환을 거치므로 `"Over Fitting"`도 정답이 된다.

### 향후 개선: 파인튜닝 기반 의미 채점

주관식 정답률이 40.7%인데, 실제로 맞는데 표기가 달라 틀린 케이스가 상당수다. 73,848건의 답변 데이터에서 유의미한 오답 약 8,000~12,000건을 추출해 "동의어 사전"을 구축하고, 이를 학습 데이터로 Llama 파인튜닝을 계획하고 있다.

## 12. AI 도구 활용 전략: "어디에 토큰을 쓸 것인가"

### 고민

Claude Code Pro 요금제에는 토큰 한도가 있다. 4시간 안에 완성하려면 토큰을 효율적으로 배분해야 했다.

### 자원 배분 결정

| 에이전트 | 토큰 소모 | 사용 여부 | 판단 근거 |
|---------|----------|----------|----------|
| UI 프로토타입 생성 | 높음 | 미사용 | 멀티 페르소나 평가까지 포함하면 토큰 대량 소모 |
| 디자인 평가 | 높음 | 미사용 | UI 품질 < 기능 완성이 우선 |
| 코드 구현 | 중간 | 사용 | 핵심 — 기능 구현에 집중 |
| 코드 리뷰 | 낮음 | 사용 | 구현 에이전트와 독립적으로 이슈 발견 |

**트레이드오프**: "디자인 완성도 < 기능 완성도"를 의식적으로 선택했다. Tailwind CSS로 Claude Code가 직접 UI를 한 번에 생성하는 방식이 디자인 에이전트 없이도 충분히 사용 가능한 결과를 만들었다.

### "AI가 만들고 AI가 잡는" 워크플로우

이 프로젝트의 모든 코드는 Claude Code가 생성했다. 구현 에이전트와 리뷰 에이전트가 분리되어 있어 "코드를 쓴 AI"와 "검토하는 AI"가 독립적으로 동작한다. 배치 저장의 동시성 이슈(§7)도 리뷰 에이전트가 발견한 것이다.

이 구조에서 사람의 역할은 **의사결정자**다. AI가 제시한 이슈와 대안 중에서 어떤 방향을 택할지, 리뷰의 HIGH 이슈를 패치할지 설계를 원점 재검토할지를 판단하는 것이 사람의 몫이다.
