## 1. 포트폴리오 본문 초안

### AI 에이전트 개발 하니스 — AI가 쓴 코드를 검수 가능한 상태로 유지하기

**기술스택**: Claude Code, 서브에이전트 30개, 슬래시 커맨드 28개, Python 훅 3종, Git 심링크 배포

---

#### 문제

AI가 코드를 빨리 써준다는 것과, 그 코드를 믿을 수 있다는 것은 다른 문제입니다.

- 1인 개발에는 2차 검토자가 없습니다.
- AI 출력은 **그럴듯해서** 더 위험합니다. 어설픈 코드는 눈에 띄지만, 그럴듯한 코드는 그냥 통과합니다.
- 세션이 끝나면 맥락이 사라집니다. 지난주에 내린 결정을 이번 주에 다시 뒤집습니다.

빨리 만드는 것은 이미 됐고, 문제는 **속도를 유지한 채로 검수 가능한 상태를 만드는 것**이었습니다.

---

#### 해결 — 규칙을 대화가 아니라 파일에 고정했다

프롬프트로 매번 지시하는 대신, 개발 규칙과 검증 절차를 저장소로 만들어 Git으로 관리하고 심링크로 전 프로젝트에 배포했습니다. 규칙 원본을 고치면 모든 프로젝트에 즉시 반영됩니다.

**역할 분리.** 에이전트 30개를 5개 도메인으로 나누고, 각 정의 파일에 "담당"과 **"담당하지 않음"**을 함께 적었습니다. 오케스트레이터는 코드를 직접 쓰지 않고 라우팅만 합니다. 진단 에이전트는 코드를 수정하지 않고 진단서만 남깁니다. 권한을 좁혀야 결과를 검수할 수 있습니다.

```
기획 → 설계 → 구현 → 리뷰 → 빌드 → 테스트 → 문서화
        ★      │      │              │
        승인    └── 실패 시 원인 분석 후 일괄 수정 ──┘
```

**게이트.** 각 단계에 산출물과 성공 조건을 정의했습니다. 미달이면 해당 에이전트를 1회 재호출하고, 2회째에도 실패하면 사람에게 넘깁니다. 무한 재시도를 막는 장치입니다.

**정지 조건.** 자동 진행이 멈춰야 하는 시점을 미리 정의했습니다.

- 수정 3회 초과
- 수정이 새 테스트 실패를 유발(회귀) → 되돌리고 재분석
- 같은 에러를 2회 고쳤는데 안 잡힘 → 증상 수정 중단, 근본 원인 탐색으로 전환

**노이즈 억제.** 리뷰 에이전트는 실제 문제일 확률 80% 이상인 항목만 보고합니다. 진단 에이전트는 검증 방법이 없는 가설은 아예 기록하지 않습니다. AI 검토의 실패 모드는 놓치는 것보다 **과잉 보고로 신뢰를 잃는 것**이었습니다.

**하니스 자체 검증.** 설정 저장소에 pre-commit 훅을 걸어, 문서의 경로 참조가 실제로 존재하는지·에이전트 정의가 스키마를 지키는지·참조되지 않는 고아 문서가 있는지를 커밋마다 검사합니다. 설계 결정은 ADR 6건으로 남겼습니다.

**지식 순환.** 에러 기록과 학습 노트를 남기고, 그중 사전 차단 가능한 것은 lint·타입 설정으로 승격시킵니다. 단 **3개 이상 프로젝트에서 같은 규칙이 반복될 때만** 전역 템플릿에 반영합니다. 1회성 사고로 전역 규칙을 늘리면 새 프로젝트 시작 비용만 커집니다.

---

#### AI Quiz에 적용 — 게이트를 끈 판단과 켠 판단

이 프로젝트의 핵심은 파이프라인을 전부 돌린 것이 아니라, **언제 끄고 언제 켜는지 판단한 것**입니다.

| 구간 | 상태 | 판단 |
|---|---|---|
| MVP 4시간 | 디자인·평가·자동테스트 에이전트 **OFF** | 토큰은 유한 자원. 기획·아키텍처·데이터 설계에 몰았다 |
| 운영 2주 | 리뷰·E2E·QA 에이전트 **ON** | 사용자가 붙은 뒤에는 회귀 비용이 개발 비용보다 크다 |

문제 데이터도 같은 구조로 만들었습니다. 교재 기반으로 **AI가 초안, 최종 판정은 사람**. 12카테고리 1,160문제를 이 파이프라인으로 운영했습니다.

저장소에 남은 실행 흔적: 에러 기록 9건, 학습 노트 7건, E2E 결과 3회분.

---

#### 결과, 그리고 한계

리뷰 에이전트가 **배치 저장의 동시성 버그**를 잡았습니다. 화면상으로는 정상 동작해서 기능 테스트로는 걸리지 않는 종류였습니다. 자동화가 값을 한 지점이 여기입니다.

한계는 더 분명했습니다.

**1. 생략해도 되는 게이트와 안 되는 게이트가 다르다.**
디자인 평가는 생략해도 Tailwind 기반으로 반응형 3단계·다크모드·키보드 네비게이션까지 나왔습니다. 반면 구현물을 리뷰 에이전트로 검증하는 단계는 생략하면 안 되는 것이었습니다. 둘의 차이는 **결함이 눈에 보이는가**입니다.

**2. AI가 빨라지면 한 번에 너무 많이 배포하게 된다.**
PWA·배치 저장·RLS 수정을 한 번에 올렸다가 원인 분리가 안 돼 롤백했습니다. 도구가 빨라진 만큼 배포 단위를 **의식적으로 잘게 유지**해야 했습니다. 이 사고 이후 롤백 규칙을 `git revert` 기반으로 명문화했습니다.

**3. 내가 검수할 수 없는 코드는 자산이 아니라 부채다.**
그래서 큰 작업은 구현 진입 전에 자가 진단을 넣었습니다. 기준은 "100% 이해"가 아니라 검수 가능 수준 3가지 — 각 블록의 의도를 한 문장으로 말할 수 있는가, 엣지 케이스를 1개 이상 짚을 수 있는가, 일부를 변형했을 때 동작을 예측할 수 있는가. 미달이면 학습 노트를 쓰고 들어갑니다.

**4. 토큰은 유한한 자원이고, 자동화 설계는 곧 예산 배분 설계다.**
"무엇을 자동화할 수 있는가"보다 "이 작업에 어디까지 쓸 것인가"가 실제 의사결정이었습니다.

## 2. 배치 제안

기존 포트폴리오 구조 기준:

```
MAIN PROJECTS
  AI 퀴즈
  텔레파시
01 출시 전 보안 감사
02 TypeScript 마이그레이션
03 측정·검증
04 AI 에이전트 개발 하니스   ← 여기 (신규)
INTERNAL TOOLS
```

**근거**: 01~03이 모두 "AI로 만든 결과물을 어떻게 검증했는가" 사례입니다. 04는 그 검증을 **개별 사례가 아니라 상시 시스템으로 만든 이야기**이므로 03 뒤에 놓으면 사례 → 시스템으로 자연스럽게 올라갑니다.

AI 퀴즈 본문에는 한 줄만 추가하고 링크로 넘기는 편이 좋습니다:

> 이때 쓴 에이전트 파이프라인과 게이트를 끄고 켠 판단은 [04]에 정리했습니다.

## 3. 예상 질문과 답변 준비

| 질문 | 핵심 답변 |
|---|---|
| "에이전트 30개, 과설계 아닌가요?" | 한 번에 만든 게 아니라 사고 1건당 규칙 1개씩 늘렸습니다. 3개 프로젝트에서 반복될 때만 전역 승격하는 기준을 둔 이유가 그겁니다. |
| "AI가 다 짜면 본인 실력은?" | 검수 가능 수준을 기준으로 뒀습니다. 못 읽는 코드는 안 받습니다. TypeScript 마이그레이션(02)에서 타입 커버리지 0 → 75.6%가 그 결과입니다. |
| "실제로 효과가 있었나요?" | 리뷰 에이전트가 잡은 동시성 버그, 보안 감사에서 나온 CRITICAL 6건. 둘 다 기능 테스트로는 안 걸립니다. |
| "한계는요?" | 위 4가지. 특히 2번(배포 단위)이 도구가 빨라져서 **새로 생긴** 문제입니다. |
| "미리캔버스에서 어떻게 쓸 건가요?" | 온톨로지 검수 백오피스는 AI 초안 + 사람 최종 판정 구조입니다. AI Quiz의 1,160문제 검수 파이프라인과 같은 모양이라 바로 대입됩니다. |
