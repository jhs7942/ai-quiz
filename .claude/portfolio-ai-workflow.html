AI가 쓴 코드를 검수 가능한 상태로 유지하기

개인 하니스 · 상시 운영
Claude Code 서브에이전트 30 슬래시 커맨드 28 Python 훅 3종 Git 심링크 배포

AI가 코드를 빨리 써준다는 것과 그 코드를 믿을 수 있다는 것은 다른 문제입니다. 1인 개발에는 2차 검토자가 없고, AI 출력은 그럴듯해서 더 위험합니다. 어설픈 코드는 눈에 띄지만 그럴듯한 코드는 그냥 통과합니다.
그래서 규칙을 프롬프트가 아니라 파일에 고정했습니다. 개발 규칙과 검증 절차를 저장소로 만들어 Git으로 관리하고, 심링크로 전 프로젝트에 배포합니다. 원본을 고치면 모든 프로젝트에 즉시 반영됩니다.

01 권한을 좁혀야 결과를 검수할 수 있다 에이전트 30개 ▼
문제
  • 한 에이전트에 전권을 주면 출력이 넓어져 검수 지점을 잡을 수 없었습니다.
  • 세션이 끝나면 맥락이 사라져, 지난주에 내린 결정을 이번 주에 다시 뒤집었습니다.
해결

역할 경계를 정의 파일에 명시

  • 에이전트 30개를 5개 도메인(개발·문서·기획·블로그·범용)으로 분리하고, 각 정의에 “담당”과 “담당하지 않음”을 함께 기재
  • 오케스트레이터는 코드를 직접 쓰지 않고 라우팅만 — 진단 에이전트는 코드를 고치지 않고 진단서만 남김

하니스 자체를 CI로 검증

  • 설정 저장소에 pre-commit 훅 — 문서의 경로 참조 실재 여부, 에이전트 정의의 스키마 준수, 참조되지 않는 고아 문서를 커밋마다 검사
  • 세션 훅 3종으로 맥락 연속성 확보 (시작 시 메모리 로드 · 종료·압축 시 저장 · 에이전트 호출 로그)
결과
  • 설계 결정 ADR 6건으로 기록 — 같은 논의를 반복하지 않음
  • 에러 기록과 학습 노트 중 사전 차단 가능한 것만 lint·타입 설정으로 승격. 단 3개 이상 프로젝트에서 반복될 때만 전역 규칙화 — 1회성 사고로 규칙을 늘리면 새 프로젝트 시작 비용만 커집니다
02 AI 퀴즈 — 게이트를 끈 판단과 켠 판단 4시간 → 운영 2주 ▼
문제
  • 파이프라인을 전부 돌리면 4시간 안에 못 끝냅니다. 토큰도 유한한 자원이었습니다.
  • 반대로 전부 끄면, 사용자가 붙은 뒤의 회귀 비용이 개발 비용보다 커집니다.
해결

구간별로 게이트를 다르게 걸었습니다

  • MVP 4시간 — 디자인·평가·자동테스트 에이전트 OFF. 토큰을 기획·아키텍처·데이터 설계에 몰았습니다
  • 운영 2주 — 리뷰·E2E·진단 에이전트 ON. 사용자가 붙은 뒤에는 판단 기준이 바뀝니다

문제 데이터도 같은 구조

  • 교재 기반으로 AI가 초안, 최종 판정은 사람 — 12카테고리 1,160문제를 이 파이프라인으로 운영
결과
  • 리뷰 에이전트가 배치 저장의 동시성 버그를 검출 — 화면상 정상 동작해 기능 테스트로는 걸리지 않는 종류였습니다. 자동화가 값을 한 지점이 여기입니다
  • 저장소에 남은 실행 흔적 — 에러 기록 9건, 학습 노트 7건, E2E 결과 3회분
03 한계 — 도구가 빨라져서 새로 생긴 문제 생략하면 안 되는 게이트 ▼

1. 생략해도 되는 게이트와 안 되는 게이트가 다르다

디자인 평가는 생략해도 Tailwind 기반으로 반응형 3단계·다크모드·키보드 네비게이션까지 나왔습니다. 반면 구현물을 리뷰 에이전트로 검증하는 단계는 생략하면 안 되는 것이었습니다. 둘의 차이는 결함이 눈에 보이는가입니다.

2. AI가 빨라지면 한 번에 너무 많이 배포하게 된다

PWA·배치 저장·RLS 수정을 한 번에 올렸다가 원인 분리가 안 돼 롤백했습니다. 도구가 빨라진 만큼 배포 단위를 의식적으로 잘게 유지해야 했습니다. 이 사고 이후 롤백 절차를 git revert 기반으로 명문화했습니다.

3. 내가 검수할 수 없는 코드는 자산이 아니라 부채다

그래서 큰 작업은 구현 진입 전에 자가 진단을 넣었습니다. 기준은 “100% 이해”가 아니라 검수 가능 수준 3가지입니다 — 각 블록의 의도를 한 문장으로 말할 수 있는가, 엣지 케이스를 1개 이상 짚을 수 있는가, 일부를 변형했을 때 동작을 예측할 수 있는가. 미달이면 학습 노트를 쓰고 들어갑니다.

4. 자동화 설계는 곧 예산 배분 설계다

“무엇을 자동화할 수 있는가”보다 “이 작업에 어디까지 쓸 것인가”가 실제 의사결정이었습니다. 토큰이 유한한 이상, 파이프라인 설계는 기술 문제가 아니라 자원 배분 문제에 가까웠습니다.

이 하니스를 관통하는 원칙

  • 경계 — 에이전트마다 “담당하지 않음”을 함께 적는다. 권한이 좁아야 출력을 검수할 수 있다
  • 정지 — 자동화의 핵심은 진행이 아니라 멈추는 조건을 미리 정의하는 것이다
  • 보수성 — 확률 80% 미만은 보고하지 않고, 검증 방법 없는 가설은 남기지 않는다. 과잉 보고가 신뢰를 먼저 깎는다
  • 누적 — 사고 1건이 규칙 1개가 되지만, 3개 프로젝트에서 반복될 때만 전역으로 올린다
