React 19 TypeScript Zustand Vite Supabase / PostgreSQL Claude Code

싸피에서 AI 시험 이틀 전, 교육생들은 시험 대비를 위해 각자 생성형 LLM으로 기출 문제를 만들어 풀고 있었습니다.
기출 문제를 만들기 위해 각자 시험 범위를 지정해야 했고, 실제 배웠던 내용이 아닌 부분도 생성될 수 있었으며, 제작에만 약 10분이 소요되었습니다.
그마저도 환경상 PC에서만 가능해, 이동 중과 같은 자투리 시간을 활용할 수 없었습니다.

이에 비효율성을 느껴, 미리 검수한 문제로 문제은행 사이트를 만들어 공유하면 모든 교육생에게 도움이 될 것이라고 생각했습니다.
시험까지 이틀이 남았기에 실사용 기간을 고려하여, 기획과 배포를 포함한 개발 기간을 4시간으로 잡고 Claude Code로 개발했습니다.

이 프로젝트는 서울에서 시작해 부산 · 광주 등 전국 캠퍼스에서도 활용되었으며, 2주간 신고와 지표를 보며 개선했습니다.

디자인 시안 토큰 소모가 가장 큰 구간이라 생략했습니다. 문제를 읽고 푸는 데 지장이 없으면 충분하다고 기준을 정하고, 시안 없이 바로 구현했습니다.

실시간 매칭과 채팅, 환불 계좌 암호화, SMS 인증까지 갖춘 백엔드를 만들고 개선을 이어가고 있습니다.

설계 게스트에게는 FK를 걸 수 없다 부채와 상환 계획 ▼
문제
  • 익명이 핵심 가치라 가입을 세울 수 없었는데, 매칭 · 채팅 · 신고 · 재선택이 전부 식별자를 전제하고 있었습니다.
  • "익명"은 다른 사용자에게 익명이라는 뜻이지, 시스템에게까지 익명이라는 뜻은 아니었습니다.
  • 교과서적 해법인 users 게스트 행은 회원을 전제로 만든 스키마에 가짜 유니크 값과 빈 비밀번호를 밀어넣는 일이었습니다.
해결
  • 게스트를 DB에 저장하지 않고 신원 전체를 JWT에 담았습니다. 진입 시 DB 쓰기 0회, 이탈 게스트를 지우는 배치도 필요 없습니다.
  • 닉네임 변경까지 DB가 아니라 토큰 재서명으로 처리해, 토큰을 신원의 단일 출처로 유지했습니다.
  • HTTP와 소켓이 같은 decodeToken을 쓰는 단일 검증 지점을 두고, 그 위에 requireMember · requireSession 두 단계만 얇게 쌓았습니다.
대가
  • 게스트는 users에 행이 없어 어떤 테이블도 FK로 참조할 수 없습니다. 게스트 본인은 단어장을 가질 수 없고, 상대가 게스트면 partner_id는 null입니다.
  • 큐에 role 컬럼이 없어 username === user_id로 게스트를 간접 추론합니다. 데이터 형태로 판별하는 것이라 취약하고, 알고 있어 문서에 남겼습니다.
  • 갚을 계획을 세워뒀습니다 — actors · users · user_credentials 분리로 세 파장이 한꺼번에 해소됩니다.

측정 재보니 느리지 않았다 느림 아닌 구조 ▼
문제
  • 폼이 느리다고 짐작하고 바꾸려다 먼저 재봤습니다. Profiler로 측정하니 글자당 정확히 1회 리렌더, 12글자에 커밋 12회가 두 번 다 재현됐습니다.
  • 그런데 한 커밋이 1.6~3.8ms로 60fps 예산(16.7ms) 안이었습니다. 지금 버벅이지 않는다는 뜻이라, "느려서 고친다"는 근거가 사라졌습니다.
  • 대신 코드를 열어보니 검증이 전부 제출 핸들러에 뭉쳐 있었고, form 태그는 0개, 중복 제출을 막는 장치도 없었습니다.
해결
  • 도입 근거를 "느린 것을 고친다"가 아니라 "폼이 커져도 리렌더가 늘지 않는 구조"로 다시 세우고 React Hook Form으로 옮겼습니다.
  • zod 같은 스키마 라이브러리는 배제했습니다. 내장 rules로 충분한데 gzip 미적용 상태라 번들 증가에 민감했습니다.
  • 오류 출처는 셋으로 늘었지만(검증 규칙 · 필드 특정 가능한 서버 응답 · 특정 불가) 표시 경로는 입력창 하단 인라인 하나로 통일했습니다.
결과
  • useState 17개 → 4개, form 0개 → 5개, autoComplete 0개 → 10개. 오류는 모달 하나씩에서 필드별 인라인 동시 표시로 바뀌었습니다.
  • 옮기다 결함 둘이 드러났습니다 — 중복검사 통과 뒤 아이디를 바꿔도 결과가 유효한 채 남는 문제, 페이지마다 다른 비밀번호 정책(8자 계정이 6자로 약화 가능).
  • 다만 전환 후 리렌더는 아직 재지 않았습니다. Before를 재놓고 After를 안 잰 채 개선했다고 쓰면 재본 의미가 없어서, 측정 조건만 미리 적어뒀습니다.

확장 인스턴스를 늘리면 매칭 큐가 갈라진다 한계와 확장 경로 ▼
한계
  • 매칭은 15초 라운드에 같은 단어를 고른 두 사람을 짝짓는데, 대기 풀을 단일 인스턴스 메모리에 들고 있습니다. 인스턴스를 늘리면 같은 단어를 고른 두 사람이 다른 인스턴스에 붙어 못 만납니다 — 풀도 소켓 이벤트도 인스턴스별로 갈라지기 때문입니다.
지금
  • 아직 본격 운영 전이라 우선 단일 인스턴스로 둡니다. 없는 부하를 겨냥해 인프라부터 늘리기보다, 필요해지는 시점에 확장하는 쪽이 낫다고 봤습니다.
확장
  • 고도화 단계에서 수평 확장이 필요해지면 세트로 갑니다 — Socket.IO Redis adapter로 인스턴스 간 이벤트를 잇고, 매칭 풀을 공유 저장소로 옮겨 짝짓기를 전역화합니다. 알고 있어 미리 적어뒀습니다.
